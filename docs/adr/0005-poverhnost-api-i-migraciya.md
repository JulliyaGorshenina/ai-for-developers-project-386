# ADR 0005: Поверхность API и переход на контракт-first с заменой схемы

- **Дата:** 2026-10-23
- **Статус:** принято

## Контекст

Реализация Design First потребовала зафиксировать поверхность API и стратегию
миграции (решения тикетов о поверхности контракта и совместимости). Контракт —
TypeSpec (`spec/main.tsp`) → OpenAPI 3.1 (`spec/openapi/openapi.json`) → TS-клиент
(`@hey-api/openapi-ts`) и Pydantic-модели (`datamodel-code-generator`). Владелец —
предзаданный профиль без входа (решение по сущностям), поэтому `X-Admin-Token`
больше не нужен.

## Решение

- **Префикс `/api`, без версии; имена полей — `snake_case`.** Версионирование
  отложено.
- **Публичные (гость):**
  - `GET /api/event-types`
  - `GET /api/event-types/{id}/availability?days=14`
  - `GET /api/event-types/{id}/slots?date=YYYY-MM-DD`
  - `POST /api/bookings` → `201` · `400` вне расписания/в прошлом · `404` нет типа …
    `409` конфликт · `422` валидация
- **Владельца (без аутентификации):**
  - `POST/PUT/DELETE /api/event-types` (`201`/`200`/`204`, `404`, `409`)
  - `GET/PUT /api/schedule`
  - `GET /api/bookings?upcoming=true`, `DELETE /api/bookings/{id}`
- **`X-Admin-Token` удалён** вместе с `auth.py` и отдельным роутером `/api/admin/*`.
- **Старые `GET /api/availability` и `GET /api/slots` заменены** scoped-по-типу
  эндпоинтами (обратная совместимость не сохраняется).
- **Big-bang миграция схемы:** таблица `event_types`, `bookings.event_type_id`;
  уникальный индекс по `slot_start` убран (конфликт считается по пересечению
  интервалов, см. ADR 0003). Старые брони не сохраняются.
- **Сгенерированное коммитится:** `spec/openapi/`, `frontend/src/api/generated/`,
  `backend/app/generated/` — машинные, руками не правятся; дрейф ловится в CI
  (`git diff --exit-code` после перегенерации).
- **Порядок изменения контракта:** правка TypeSpec → генерация → код обеих сторон.

## Последствия

- Фронтенд ходит в API только через сгенерированный SDK (`frontend/src/api.ts` —
  тонкая обёртка над ним).
- Правила бронирования (расписание, сетка, занятость) обеспечиваются сервером;
  сгенерированные Pydantic-модели несут валидацию из контракта.
- Сборка владельца: типы встреч засеиваются по умолчанию (`consultation` 30 мин,
  `deep-dive` 60 мин) и управляются на странице владельца.
- Паттерн «Design First»: реализация на обеих сторонах выводится из одного
  источника; расхождения всплывают на дрейф-гарде, а не на живом приложении.
